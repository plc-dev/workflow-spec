# Spike 1.2e — LOAD/SCALE CHECK for the Postgres-native pattern

**Task**: tasks.md 1.2e. The one claim spike 1.2 deliberately left untested:
operational weight under real(ish) load - narrowly scoped (like 1.2a was
originally), not a production-capacity-planning exercise. See
`FINDINGS.md` for the correctness/atomicity results this builds on.

## What was built

`src/test-load.js` extends the same schema/worker (`worker.js`,
unmodified) from spike 1.2 with:

- `src/monitor.js`: polls `pg_stat_activity` every 250ms during the run to
  track peak concurrent backend count and peak/average concurrent
  lock-waiters (`wait_event_type = 'Lock'`).
- A seeding step that interleaves many more sessions' executions than
  spike 1.2's contention test (60 sessions x 100 executions = 6,000 rows,
  vs. 2 sessions x 40 = 80 previously - ~75x).
- A worker pool of 32 concurrent workers (vs. 8 previously - 4x), against
  a Postgres instance whose `max_connections = 100` (confirmed via `SHOW
  max_connections`).
- A dedicated **churn phase**: 4,000 `BEGIN; UPDATE ...; ROLLBACK;`
  operations (16 concurrent workers) against a fixed set of 25 "hot" rows,
  to generate dead tuples directly and check whether they're reclaimable.

## Results

Run reproducibly against a real Postgres 16 instance (`npm run test:load`,
exit code 0 on every run):

### 1. Throughput & correctness at scale

All 6,000 executions processed exactly once in ~2.3s (~2,590/sec on this
single-instance, unremarkable-hardware Docker container), and **all 60
session chains came out contiguous** - the D3 linear-per-session-mutation
guarantee spike 1.2 already proved at small scale did not quietly break at
~75x the row count.

### 2. Connection-count ceiling

Peak concurrent backends observed: **33** (32 workers + monitor + a
transient extra), against `max_connections = 100` - comfortably under the
80% threshold this check used as a red line. No connection-exhaustion
errors at any point.

### 3. Lock contention at scale

Peak concurrent lock-waiters: **26-28** (varies slightly run to run) out of
32 workers, average ~20-22 across the run. This is expected and benign,
**not a red flag**: with 60 sessions and 32 workers, many workers are
racing for the *same* session's pointer row at any given moment purely by
the pigeonhole principle (32 workers > cases where a session has few
remaining rows), so a meaningful fraction of workers waiting on a
`FOR UPDATE` row lock at any instant is exactly what per-session
serialization is supposed to look like under this load shape. The number
that would have been concerning is a **stuck** or ever-growing lock-wait
count, which did not occur - the run completed in ~2.3s with all locks
eventually granted and released.

### 4. Dead-tuple / bloat behavior under sustained UPDATE churn

- Before the churn phase: `n_dead_tup ≈ 10,600` (from the main run's own
  ~2 updates/row on 6,000 executions rows).
- After 4,000 rollback-churn updates on 25 hot rows: `n_dead_tup` increased
  by **~700-770** (not the full 4,000 - see caveat below).
- After a manual `VACUUM ANALYZE`: `n_dead_tup = 0`, `n_live_tup = 6,000`.

**Dead tuples generated by churn were fully reclaimable.** The pattern's
reliance on UPDATE-in-place (status transitions on `executions`, upserts on
`placement`) does not create unreclaimable bloat - ordinary Postgres
vacuuming handles it as expected.

**Caveat on the exact churn count**: the observed dead-tuple increase
(~700-770) was consistently lower than the raw 4,000 rollback iterations
across repeated runs, even after waiting past Postgres's per-backend
statistics-flush throttling (~1s, confirmed necessary - an earlier version
of this test read stale `pg_stat_user_tables` counters immediately after
the churn burst and showed *zero* change, which was a measurement artifact,
not a real finding, and is why the script now waits ~3s before reading
"after" stats). The remaining gap between 4,000 iterations and ~700-770
recorded dead tuples is most likely Postgres's HOT-update optimization
(an update that doesn't touch an indexed column and fits on the same page
can avoid creating a new dead tuple in some cases) rather than a flaw in
the churn methodology - this spike did not chase the exact mechanism
further, since the qualitative result (churn increases dead tuples; VACUUM
fully reclaims them) is what the task scoped to check, not exact tuple
accounting.

## Verdict

**No showstopper found at this scale.** All four checks the task named
hold:

1. Connection ceiling: comfortable headroom (33/100, well under the 80%
   red line) at 32 concurrent workers.
2. Lock contention: scales as expected (more waiters with more sessions
   sharing fewer workers), with no evidence of pathological/stuck
   contention.
3. Correctness (D3 linear-per-session-mutation): unbroken at ~75x spike
   1.2's original scale.
4. Dead-tuple/bloat: churn from UPDATE-in-place is real but fully
   reclaimable via ordinary `VACUUM` - no structural bloat problem.

This closes the one item spike 1.2 explicitly left open before treating
the Postgres-native path's "lightest operational footprint" claim (design
.md D6) as more than a paper claim.

## What this does NOT settle

- This is single-instance, single-machine, Docker-container-scale testing
  (thousands of rows, tens of workers, seconds of wall-clock time) - not a
  production capacity-planning exercise (no multi-node Postgres, no
  realistic network latency/jitter, no long-duration soak test, no test at
  the orders-of-magnitude-larger row counts a real production system would
  eventually accumulate in `session_log`/`checkpoints` history tables).
- Autovacuum's *default schedule* (1-minute naptime) was not evaluated
  directly - this test forced a manual `VACUUM ANALYZE` to check dead
  tuples are reclaimable *at all*, which is the viability question; whether
  the default autovacuum schedule keeps up under sustained production
  traffic is a tuning question for later, not a viability blocker now.
- Growth/retention strategy for `session_log`/`checkpoints` over the life
  of many long-lived sessions (not just a burst of 6,000 short-lived
  executions) was not exercised - this is more D3's TTL/GC concern (3.6,
  3.11) than this spike's scope.

## How to reproduce

`npm run test:load` is fully self-contained (starts/tears down its own
Postgres container via `../../scripts/with-postgres.sh` - see that module's
main `FINDINGS.md` for how the shared lifecycle wrapper works):

```bash
npm install
npm run test:load
# tune scale via env vars, e.g.:
LOAD_SESSIONS=200 LOAD_PER_SESSION=200 LOAD_CONCURRENCY=64 npm run test:load
```
