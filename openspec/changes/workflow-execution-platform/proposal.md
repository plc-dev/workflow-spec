## Why

We have a continuously growing set of dockerized, stateless-function services (REST API + CLI, discoverable via OpenAPI, indexed in this platform's own service registry). An external frontend needs to run these functions - individually or composed into workflows - against a mix of user-provided, static, and session-manipulated data. Today there is no system to: (a) declare workflows over these service images, (b) execute them reliably across multiple machines, (c) isolate user/session data from static data without baking session logic into every service, or (d) scale/pool containers on demand without corrupting that isolation. This proposal captures the architecture explored to address all of the above, including engine selection, state/session handling, scheduling/placement strategy, secrets injection, service registry ownership, workflow-spec storage, and the DSL's structural model.

## What Changes

- Introduce a DSL for specifying workflow-specs that compose docker service images as steps, with data bindings expressed as references to different sources (user, static, session) rather than inlined values.
- Introduce a **scope + mutability + interactivity** declaration model in the DSL: workflow-writers declare *intent* (is this binding static/session/request-scoped, is it mutable, is it interactive-latency-sensitive) rather than mechanism (no volumes, affinity, or pooling details in the DSL).
- Split the DSL into an **authoring surface** (what a workflow-writer types, potentially plural, and not required to be deterministic) and a **stable intermediate representation (execution plan)** that the scheduler and execution engine consume (steps, bindings, write declarations, secret references, outputs). The execution plan is statically shaped but supports dynamic cardinality/path via `branch` (statically enumerated cases, dynamically selected) and `map`/`forEach` (statically shaped iteration body, dynamically sized count) constructs. Every workflow-spec exposes a derivable signature (required request parameters, session-requirement, outputs), discoverable the same way service OpenAPI specs are discoverable. A `compute` binding kind evaluates a bounded, serializable **JSON-Logic** expression for pure/simple derived values (e.g. branch selectors) without invoking a service or scheduling a step execution. Given a funded UI authoring tool must be able to open and edit arbitrary existing workflow-specs, the canonical authoring format is a structured document closely mirroring the execution plan - not embedded imperative code. The execution plan carries a whole-document version tag with forward-only, lazy migration.
- Introduce an event-sourced session/state layer, external to workflow definitions:
  - User input history is the durable source of truth for a session.
  - Warm/materialized state (e.g., a loaded DB dump) is a **content-addressed snapshot cache**, rebuildable from the input history, TTL'd and garbage-collected.
  - Snapshot chains model session mutation history (linear per session, diverging across sessions from shared immutable roots); copy-on-write is used where services support incremental snapshots.
  - Session-scoped bindings may declare a seed/fallback source (e.g. a static reference) used the first time a session key is read.
  - (input-hash, operation) -> output-hash memoization enables cross-session reuse and workflow-step incrementality.
- Introduce a scheduler/placement layer that fuses three inputs to decide execution strategy per step: service capability declarations (registry/OpenAPI: mutates?, materialization cost, COW support, change-detection), workflow-writer intent (from the DSL), and runtime observations (snapshot size, access frequency). Placement/affinity is always an optimization, never a correctness requirement. The scheduler can pre-analyze every statically declared branch case and map-iteration shape ahead of execution. The concrete routing mechanism that turns a placement decision into an actually-routed call to a specific service replica is not yet designed (see design.md D4/Open Questions).
- Introduce the **service registry** as a first-party metadata index (not an image byte store - images are referenced by OCI pointer): per-image-digest OpenAPI contract (the sole stored contract; CLI/MCP surfaces are projected from it), per-function capability metadata, per-image hardware requirements (outside the capability trust-tier model), per-function nesting declarations, and a trust tier. Reads split by consistency need (interactive discovery vs. an atomic dispatch-time placement-facts read); writes split by privilege (registering a new image is platform-developer-only; updating a trust tier is reachable by the workflow platform's own conformance pipeline). Workflow-spec steps resolve to a pinned image digest at authoring time.
- Introduce the **workflow-spec store** as a first-party component distinct from the service registry: workflow-specs are stored under a namespaced URN identity + immutable version (mirroring the dataset URN scheme), exposing a derived signature for discovery, and are never registry entries. Reuse of one workflow-spec by another is by **fork**, not live reference: the source's shape/steps are copied into the forker's own namespace at authoring time, producing a self-contained workflow-spec with an immutable, transitive lineage pin back to its exact source version (provenance/upstream-awareness only, never a run-time dependency or auto-propagating update). Writer-scoped secret references never carry across a fork - a hard platform invariant following directly from the secrets-management scoping model - while static-dataset references carry over by default, since datasets are globally shared by design. Dynamic fan-out (`map`/`forEach`) is unrelated to forking and continues to use tracked child executions. Visibility, tenancy, publish-authority, fork-lineage-cycle handling, and workflow-spec-version-mismatch-on-fork are explicitly delegated to the external authoring tool or deferred as follow-up work, not solved here.
- Select a durable-execution engine whose runtime model matches long-lived sessions, warm-service invocation, sticky-but-optional affinity, native retry/backoff, native addressable warm-entity support, and bounded agent-directed composition - evaluated against Argo Workflows, Temporal, Ray, Restate, Dapr (Workflows + Actors), Hatchet, Conductor, and a Postgres-native/DBOS-shaped self-written alternative (see design.md D6). **DECIDED: a Postgres-native path (a resonate-pg-shaped fork of the documented Postgres-durable-execution pattern)**, locked in via spikes 1.2/1.2-hatchet/1.2a/1.2d/1.2e - see design.md D6 for the full evaluation and spike results. Every requirement, execution plan construct, and capability spec in this change remains written engine-agnostically, both because that discipline held up as good practice through the decision process and to keep the decision revisitable if a future finding surfaces a blocker. The engine is expected to support dynamically-started, durably-tracked child/step executions (for map constructs) without the parent execution terminating, and support for delegating batch/spawn-style steps to a secondary backend (e.g. Kubernetes Jobs) remains an option but is not committed to any specific pairing.
- Define autoscaling and container pooling (K8s + KEDA) that scales/pools per service without violating the data-isolation model established above (pooled containers must remain provably stateless between invocations, or be scoped to a specific content-addressed hash).
- Introduce scoped, reference-based secrets management: secrets are declared by name + scope (workflow-writer-owned or user-owned) in the DSL, never inlined; injected per-request into pooled containers (never via environment variables); resolved worker-side inside the step's execution so only references (not raw values) persist in durable execution history.
- Introduce **Item Pool integration**: resolve a request-scoped assessment-item-identifier (supplied by an external digital learning environment) against a trusted, external Item Pool into ordinary `static`-scope dataset bindings, via a new `itemResource` binding kind whose path addressing is arbitrarily nested (unlike the existing flat-only `request` binding rule). Resolution is eager (the whole item manifest is flattened on first reference to an instance, not lazily per path), synchronous in the request path, and memoized per item instance - a further application of the existing derived-cache-over-a-durable-source-of-truth pattern (D3/D6), now applied to an external source. Item confidentiality and the item type/instance distinction are the Item Pool's concern, not the platform's, mirroring D13's existing delegation of workflow-spec visibility/tenancy to the external authoring tool (see design.md D15/D16).
- Extend CLI-invoked function onboarding with a **mandated heavy-data transport contract** (`--data-file <path> --state-id <key>`, universal, not per-service-discovered): a deliberate, named departure from the service registry's otherwise discover-don't-assume capability model (D5), justified by the same mandatory-single-contract precedent already established for OpenAPI (D12). Ties into the existing autoscaling/pooling promote-demote lifecycle (D4a) for warm CLI-invoked services (see design.md D17). **Superseded in scope by D17a**: the software-design ADR series (`docs/adr/0005`, `0008`) makes CLI the engine's universal step-dispatch transport - every registered function, not a CLI-invoked subset - so this contract now applies to every step's heavy/dataset-scoped bindings, not only to functions a workflow-writer happens to invoke via CLI. This surfaced a real onboarding gap for the one already-identified external reference service (task 1.1's pinned SQL-execution image, confirmed REST-only) - **partially resolved, then the contract's SHAPE itself superseded by D17b**: every onboarded service must ship a native CLI, no platform-generated wrapper exception (design.md D17a) - the reference service itself still needs an upstream change before it is onboardable (no CLI surface exists at all today), tracked as a follow-up (tasks.md 1.1/2.3). **D17b then split the universal `--data-file`/`--state-id` shape itself into three layers** - unconditional materialization (unchanged), a per-function DECLARED `invocationDescriptor` (the service's own native CLI signature: flag/positional/stdin, never invented to satisfy this platform), and an opt-in per-function `stateReuse` capability (D5-style) - so a future CLI-bearing service's onboarding cost shrinks to "expose an existing operation as a CLI accepting a file path/stdin," never "implement this platform's own contract." See design.md D17b, `registry/`'s `invocation_descriptor`/`state_reuse`/`additive_warm_update` columns (a clean override of the old contract, not a migration), and tasks.md 2.12/4.8's re-corrected scope.
- Introduce **compose vs. nest** as two distinct, previously-conflated concerns: *composing* a workflow out of steps is a workflow-writer activity, reused across workflows only by forking into the workflow-spec store (above), never the registry and never a live run-time reference; *nesting* is a service function's own container code calling other registered services, declared as a possibility via the registry's `nesting_declaration` metadata and defaulting to an orchestrator-aware path, with direct-transport bypass requiring an explicit, trust-tier-reviewed exception. Agent-directed (MCP-driven) nesting is one case of this model - an ordinary step invoking a `nesting_declaration: {via: mcp, targets: open}` service, with its allowlist and governor expressed as ordinary required parameters of that service's own signature, and the concrete nested target(s) supplied as ordinary DSL bindings rather than a bespoke execution plan construct.
- **BREAKING**: None - this is a net-new platform; no existing system is being replaced.

Explicitly out of scope for this proposal (to be explored and captured separately): the full concrete authoring-surface syntax/grammar; the specific secrets-broker product (the injection model itself is in scope and decided; only the backing store is deferred); the specific OCI-compliant registry product/topology used for image byte storage (the metadata index itself is in scope; only the byte-store backing is deferred, same posture as the secrets broker); the concrete mechanism cost of orchestrator-aware nesting (coupled to D6, now decided - see below); the workflow-spec store's visibility/tenancy/publish-authority model (explicitly delegated to the external authoring tool); fork-lineage-cycle handling and workflow-spec-version-mismatch-on-fork for workflow-specs (design.md D13); and exposing this platform's registry outward as an MCP server to arbitrary third-party agent hosts (a distinct, separate idea from the agent-nesting case captured here). All are flagged as open follow-ups in design.md. (The execution engine selection itself, previously listed here as deferred, is now decided - see D6 above.)

## Capabilities

### New Capabilities
- `workflow-dsl`: A restricted-YAML/JSON-compatible authoring surface (camelCase, JSON-Schema-validated, no anchors/aliases/merge keys) for defining workflow-specs over docker service images, including data-source bindings (user/static/session), scope/mutability declarations, once-per-key `sessionState` interactivity/fallback declarations, compiled to a stable, engine-agnostic, versioned execution plan, including `branch`, `map`/`forEach` (with a `{from: item}` binding source), and `compute` (JSON-Logic) constructs, generic required-parameter validation, flat request-parameter signatures, URN-addressed static dataset references (OCI for service version pins), and derived workflow signatures.
- `session-state-management`: Event-sourced session input history, content-addressed snapshot caching, copy-on-write chains, TTL-based GC, seed/fallback bindings, session rewind with truncation-on-new-mutation, configurable checkpoint retention, and cross-session memoization of (input, operation) -> output.
- `execution-scheduling`: Placement engine fusing service capabilities, workflow intent, and runtime observations into execution strategy (spawn vs. warm pool, shared vs. isolated, affinity routing as optimization), including pre-analysis of statically declared branch/map possibilities, tunable promotion/demotion thresholds, and capability-declaration trust-tier gating.
- `workflow-execution-engine`: Distributed, multi-machine execution of instantiated workflows with durable execution, native retries/backoff, support for both spawned (stateless) and warm-service (pooled) step invocation, and dynamically-started child executions that do not terminate the parent.
- `autoscaling-pooling`: Per-service autoscaling and container pre-warming/pooling under Kubernetes/KEDA, constrained to preserve the data-isolation model.
- `secrets-management`: Scoped (workflow-writer / user), reference-based secret injection into steps, resolved worker-side and kept out of durable execution history.
- `service-registry`: First-party metadata index over service images (byte storage deferred, OCI-reference pointer): per-digest OpenAPI contract as sole stored contract, per-function capability metadata, per-image untiered hardware requirements, per-function nesting declarations, digest-pinned resolution, atomic placement-facts reads, and privilege-split register/trust-tier writes.
- `workflow-spec-store`: First-party store for workflow-specs, distinct from the service registry: namespaced URN identity with immutable versions, derived-signature discovery, reuse by fork (self-contained copy + immutable, transitive lineage pin, never a live reference), a hard platform invariant that writer-scoped secrets never carry across a fork (dynamic fan-out remains child-executed, unrelated to forking), no trust-tier model.
- `service-nesting`: A mandatory-by-default, declared-exception policy for a service nesting calls to other registered services; dispatch-time allowlist and durable governor enforcement for open-target nesting services; MCP as one transport realization among others.
- `item-pool-integration`: Resolution of a request-scoped assessment-item-identifier against an external, trusted Item Pool into ordinary static-dataset bindings via a new `itemResource` binding kind; eager, memoized, whole-item flattening into the existing dataset resource catalog; arbitrarily-nested path addressing into a flattened item manifest; item confidentiality and item-type/instance shape consistency delegated entirely to the Item Pool and external authoring tooling, never a platform invariant.

(none - no existing specs in this repo)

## Impact

- New control-plane components: DSL compiler/validator (authoring-surface-to-execution-plan), scheduler/placement service (plus a not-yet-designed placement-routing mechanism), content-addressed snapshot store, session event log, secrets broker integration, nesting-enforcement layer (allowlist/governor dispatch, MCP gateway), the service registry itself (metadata index, register/trust-tier write paths), the workflow-spec store (URN identity/version store, fork operation + lineage-pin tracking), and an Item Pool integration/flattening component that mirrors resolved item-instance resources into the existing dataset resource catalog.
- New external dependency on an Item Pool service (trusted upstream infrastructure, product/protocol not selected here - see design.md D15 Open Questions), introducing a synchronous, latency-adding, availability-coupled call into the student-facing request path for any workflow using `itemResource` bindings.
- New dependency on a durable-execution engine - DECIDED: a Postgres-native path (resonate-pg-shaped fork), see design.md D6; Kubernetes + KEDA remain the compute substrate.
- New dependency on a secrets broker/store (specific product not yet selected - kept agnostic).
- New dependency on a standard OCI-compliant registry for image byte storage/pull-auth/replication/GC (product/topology deferred, same posture as the secrets-broker product) - the service registry itself only stores a pointer to it.
- Existing dockerized services are unaffected in isolation but are expected to expose capability metadata (mutation, materialization cost, COW support, change-detection, nesting transport/targets) and hardware requirements via their OpenAPI/registry entries to participate fully in the placement and nesting models.
- Follow-on design work required (tracked as open questions, not blocking this proposal): concrete authoring-surface syntax; specific secrets-broker product selection; the concrete mechanism cost of orchestrator-aware nesting (coupled to D6, now decided); the placement-routing mechanism (coupled to D6, now decided - see 1.10); outward-facing MCP exposure of the registry to third-party agent hosts (a distinct, separate idea); the workflow-spec store's visibility/tenancy/publish-authority model (delegated to the external authoring tool); fork-lineage-cycle handling and workflow-spec-version-mismatch-on-fork for workflow-specs (design.md D13). (Execution engine selection, previously listed here, is now decided - see D6.)
