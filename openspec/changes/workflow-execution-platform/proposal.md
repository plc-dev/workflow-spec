## Why

We have a continuously growing set of dockerized, stateless-function services (REST API + CLI, discoverable via OpenAPI in a registry). An external frontend needs to run these functions - individually or composed into workflows - against a mix of user-provided, static, and session-manipulated data. Today there is no system to: (a) declare workflows over these service images, (b) execute them reliably across multiple machines, (c) isolate user/session data from static data without baking session logic into every service, or (d) scale/pool containers on demand without corrupting that isolation. This proposal captures the architecture explored to address all of the above, including engine selection, state/session handling, scheduling/placement strategy, secrets injection, and the DSL's structural model.

## What Changes

- Introduce a DSL for specifying workflow-specs that compose docker service images as steps, with data bindings expressed as references to different sources (user, static, session) rather than inlined values.
- Introduce a **scope + mutability + interactivity** declaration model in the DSL: workflow-writers declare *intent* (is this binding static/session/request-scoped, is it mutable, is it interactive-latency-sensitive) rather than mechanism (no volumes, affinity, or pooling details in the DSL).
- Split the DSL into an **authoring surface** (what a workflow-writer types, potentially plural, and not required to be deterministic) and a **stable intermediate representation (IR)** that the scheduler and execution engine consume (steps, bindings, write declarations, secret references, outputs). The IR is statically shaped but supports dynamic cardinality/path via `branch` (statically enumerated cases, dynamically selected) and `map`/`forEach` (statically shaped iteration body, dynamically sized count) constructs. Every workflow-spec exposes a derivable signature (required request parameters, session-requirement, outputs), discoverable the same way service OpenAPI specs are discoverable. A `compute` binding kind evaluates a bounded, serializable **JSON-Logic** expression for pure/simple derived values (e.g. branch selectors) without invoking a service or scheduling a step execution. Given a funded UI authoring tool must be able to open and edit arbitrary existing workflow-specs, the canonical authoring format is a structured document closely mirroring the IR - not embedded imperative code. The IR carries a whole-document version tag with forward-only, lazy migration.
- Introduce an event-sourced session/state layer, external to workflow definitions:
  - User input history is the durable source of truth for a session.
  - Warm/materialized state (e.g., a loaded DB dump) is a **content-addressed snapshot cache**, rebuildable from the input history, TTL'd and garbage-collected.
  - Snapshot chains model session mutation history (linear per session, diverging across sessions from shared immutable roots); copy-on-write is used where services support incremental snapshots.
  - Session-scoped bindings may declare a seed/fallback source (e.g. a static reference) used the first time a session key is read.
  - (input-hash, operation) -> output-hash memoization enables cross-session reuse and workflow-step incrementality.
- Introduce a scheduler/placement layer that fuses three inputs to decide execution strategy per step: service capability declarations (registry/OpenAPI: mutates?, materialization cost, COW support, change-detection), workflow-writer intent (from the DSL), and runtime observations (snapshot size, access frequency). Placement/affinity is always an optimization, never a correctness requirement. The scheduler can pre-analyze every statically declared branch case and map-iteration shape ahead of execution. The concrete routing mechanism that turns a placement decision into an actually-routed call to a specific service replica is not yet designed (see design.md D4/Open Questions).
- Select a durable-execution engine whose runtime model matches long-lived sessions, warm-service invocation, sticky-but-optional affinity, native retry/backoff, native addressable warm-entity support, and bounded agent-directed composition - evaluated against Argo Workflows, Temporal, Ray, Restate, Dapr (Workflows + Actors), and a DBOS-shaped self-written alternative (see design.md D6). **This selection is an explicit open question, not a decision** - every requirement, IR construct, and capability spec in this change is written engine-agnostically so the decision can be resolved later without invalidating what's captured. The engine is expected to support dynamically-started, durably-tracked child/step executions (for map constructs) without the parent execution terminating, and support for delegating batch/spawn-style steps to a secondary backend (e.g. Kubernetes Jobs) remains an option but is not committed to any specific pairing.
- Define autoscaling and container pooling (K8s + KEDA) that scales/pools per service without violating the data-isolation model established above (pooled containers must remain provably stateless between invocations, or be scoped to a specific content-addressed hash).
- Introduce scoped, reference-based secrets management: secrets are declared by name + scope (workflow-writer-owned or user-owned) in the DSL, never inlined; injected per-request into pooled containers (never via environment variables); resolved worker-side inside the step's execution so only references (not raw values) persist in durable execution history.
- Introduce service composability: a workflow-spec may be published as a composite registry entry, invocable as a step the same way a leaf service is; inter-service composition otherwise defaults to an orchestrator-aware path, with direct-transport bypass requiring an explicit, trust-tier-reviewed exception. Agent-directed (MCP-driven) composition is one case of this model - an ordinary step invoking a "composes: {via: mcp, targets: open}" service, with its allowlist and governor expressed as ordinary required parameters of that service's own signature, not a bespoke IR construct.
- **BREAKING**: None - this is a net-new platform; no existing system is being replaced.

Explicitly out of scope for this proposal (to be explored and captured separately): the full concrete authoring-surface syntax/grammar; the specific secrets-broker product (the injection model itself is in scope and decided; only the backing store is deferred); the execution engine selection itself (deferred, D6); the concrete mechanism cost of orchestrator-aware composition (coupled to D6); and exposing this platform's registry outward as an MCP server to arbitrary third-party agent hosts (a distinct, separate idea from the agent-composition case captured here). All are flagged as open follow-ups in design.md.

## Capabilities

### New Capabilities
- `workflow-dsl`: A restricted-YAML/JSON-compatible authoring surface (camelCase, JSON-Schema-validated, no anchors/aliases/merge keys) for defining workflow-specs over docker service images, including data-source bindings (user/static/session), scope/mutability declarations, once-per-key `sessionState` interactivity/fallback declarations, compiled to a stable, engine-agnostic, versioned IR, including `branch`, `map`/`forEach` (with a `{from: item}` binding source), and `compute` (JSON-Logic) constructs, generic required-parameter validation, flat request-parameter signatures, URN-addressed static dataset references (OCI for service version pins), and derived workflow signatures.
- `session-state-management`: Event-sourced session input history, content-addressed snapshot caching, copy-on-write chains, TTL-based GC, seed/fallback bindings, session rewind with truncation-on-new-mutation, configurable checkpoint retention, and cross-session memoization of (input, operation) -> output.
- `execution-scheduling`: Placement engine fusing service capabilities, workflow intent, and runtime observations into execution strategy (spawn vs. warm pool, shared vs. isolated, affinity routing as optimization), including pre-analysis of statically declared branch/map possibilities, tunable promotion/demotion thresholds, and capability-declaration trust-tier gating.
- `workflow-execution-engine`: Distributed, multi-machine execution of instantiated workflows with durable execution, native retries/backoff, support for both spawned (stateless) and warm-service (pooled) step invocation, and dynamically-started child executions that do not terminate the parent.
- `autoscaling-pooling`: Per-service autoscaling and container pre-warming/pooling under Kubernetes/KEDA, constrained to preserve the data-isolation model.
- `secrets-management`: Scoped (workflow-writer / user), reference-based secret injection into steps, resolved worker-side and kept out of durable execution history.
- `service-composability`: Composite registry entries; a mandatory-by-default, declared-exception policy for inter-service composition; dispatch-time allowlist and durable governor enforcement for open-target composing services; MCP as one transport realization among others.

## Impact

- New control-plane components: DSL compiler/validator (authoring-surface-to-IR), scheduler/placement service (plus a not-yet-designed placement-routing mechanism), content-addressed snapshot store, session event log, secrets broker integration, composability enforcement layer (allowlist/governor dispatch, MCP gateway).
- New dependency on a durable-execution engine - which one (Temporal, Ray, Restate, Dapr, or a DBOS-shaped self-written alternative) is an open question (design.md D6); Kubernetes + KEDA remain the compute substrate regardless of the outcome.
- New dependency on a secrets broker/store (specific product not yet selected - kept agnostic).
- Existing dockerized services are unaffected in isolation but are expected to expose capability metadata (mutation, materialization cost, COW support, change-detection, composition transport/targets) via their OpenAPI/registry entries to participate fully in the placement and composability models.
- Follow-on design work required (tracked as open questions, not blocking this proposal): execution engine selection (D6); concrete authoring-surface syntax; specific secrets-broker product selection; the concrete mechanism cost of orchestrator-aware composition (coupled to D6); the placement-routing mechanism (coupled to D6); outward-facing MCP exposure of the registry to third-party agent hosts (a distinct, separate idea).
